# Add bootstrap merge guidance and report actions

## Status
Backlog

## Assignee
codex

## Parent feature
Product OS multi-product rollout readiness

## Intended outcome
Reduce operator uncertainty after bootstrap by making the generated report actionable enough to drive a manual merge pass instead of leaving sidecar files unexplained.

## Persona
Founder-operator

## Journey
Replicate the operating system across products.

## Context
The current bootstrap flow writes a summary report and sidecar files, but rollout into real repos will stall if the operator cannot quickly tell which files are safe to adopt, which need manual merging, and which can be ignored for now.

## Scope
- improve bootstrap reporting so each result points to a recommended next action
- define a concise merge-review checklist for operators adopting Product OS
- keep the report deterministic and readable in-repo

## Constraints
- do not add automated file merging in this task
- do not require external services or interactive prompts

## Acceptance criteria
- [ ] the bootstrap report distinguishes between adopt-now, review-manually, and unchanged outcomes
- [ ] merge guidance exists for the most important file classes introduced by Product OS
- [ ] the operator can complete a manual review from repo-local docs and report output

## Operational readiness
Required. Failure visibility: poor reporting leads to silent partial adoption. Recovery path: rerun bootstrap after improving report output and keep manual merge decisions explicit. Blast radius: limited to bootstrap documentation and report generation. Monitoring gap: no telemetry is needed, but the report should make rollout gaps visible.

## Implementation notes
- start from `docs/product-os-bootstrap-report.md` output generated by the bootstrap script
- keep wording aligned with `docs/delivery-system/product-os-repo-workflow.md`

## Validation
- Task type: workflow-only
- run the bootstrap command and inspect the updated report output
- inspect the merge guidance against at least one example conflict scenario
- run `npm run review:active-task` when this task becomes active
- broader product journey regression is not required because this task is repo-workflow only
